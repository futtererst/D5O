# RC12 historical integrity and recovery

**PASS for original business-field preservation and local restoration, within the captured checkpoint.** A fresh 177-entry pre-upgrade restore was the reference for the exercised 202-entry upgrade. Hash-only row multisets covered 284 original Auth, Storage, public and D5O tables. Every original key remained. Exact full-row signatures matched except seven tables: four gained only frozen-migration columns (`admin_identity_requests.expires_at`, `connected_crew_profiles.qualification_expires_on`, `memberships.revision`, and workspace profile fields); `configuration_versions` had no changed field value despite a serialized-row digest difference; `prototype_states` changed because a fictional Work was appended; and two provider-managed `storage.migrations.hash` values changed when the local Storage API started. The [row digests](evidence/D5O_RC12_HISTORICAL_ROW_DIGESTS.json), [column deltas](evidence/D5O_RC12_HISTORICAL_COLUMN_DELTAS.json), and [projection check](evidence/D5O_RC12_PROJECTION_PRESERVATION.json) retain no historical values. All 15 original catalog records and all 18 original Work projection records remained byte-equivalent as JSON entries after the fictional creation. No original Work, permit, approval, receipt, audit, invitation or private-object association was rewritten by the active tests. All 814 foreign keys remained validated.

The fresh encrypted post-upgrade checkpoint restored offline in **48.10 seconds** at 202 ledger entries, 25 historical Auth users and identities, 15 Work records, 23 object associations and matching private bytes. A separate pre-upgrade checkpoint restored in **36.93 seconds** at 177 entries. Injected SQLSTATE `P0001` after DDL rolled back the probe table and retained ledger 177, Auth users 25, Work 15 and Storage metadata 23. The restore runner was narrowly corrected to wait through a reproducible PostgreSQL initialization restart. [Post-upgrade restore](evidence/D5O_RC12_POST_UPGRADE_RECOVERY.json), [pre-upgrade restore](evidence/D5O_RC12_PRE_UPGRADE_RECOVERY.json), and [injected failure](evidence/D5O_RC12_INTERRUPTED_RECOVERY.json) give the measurements.

The original database and private-object captures were not atomic. These local timings are not production RTO/RPO. A production cutover still requires authorized write quiescence, drained commands/uploads, one database/object inventory boundary, protected snapshots and hashes, then gated migration and application verification before writes resume. The later production Auth provider ledger was copied separately for the local GoTrue test and is not an atomic part of the original checkpoint.
