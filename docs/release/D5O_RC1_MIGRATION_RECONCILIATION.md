# D5O RC1 migration reconciliation

**Gate B: FAIL for direct hosted promotion; BLOCKED for staging execution.** The 234-entry [RC0 manifest](D5O_RC0_MIGRATION_CHECKSUMS.json) is a reproducible *source* chain, not the applied hosted chain. The D5O hosted project has 177 ledger entries: 148 version/name matches, 29 hosted-only versions, and 86 source-only versions. Of the 29 hosted-only entries, 19 have one name-linked source file but a different version; the first ten are legacy `001`–`010` entries absent from the RC0 manifest. Of the 86 source-only versions, 63 are among the 211 released-source files and 23 are RC0's local forward files. Accounting for the 19 possible remappings still leaves 44 released-source versions without a clear hosted counterpart. Name similarity does not prove equal SQL.

The exact [ledger comparison](D5O_RC1_LEDGER_COMPARISON.json) identifies every version, proposed name linkage, source filename and source SHA-256. The [read-only hosted ledger](D5O_RC1_HOSTED_LEDGER_READ_ONLY.json) and [hosted statement hashes](D5O_RC1_HOSTED_LEDGER_STATEMENT_HASHES.json) preserve observations. Hosted hashes are SHA-256 of newline-joined stored `statements[]`; the RC0 hashes are raw migration-file bytes, so they are **not directly equivalent**. Two inspected version-remapped entries also differ in stored-statement versus source-file byte length. The hosted schema itself must be compared on a protected staging copy before deciding whether a file was already represented by a differently versioned operation.

The hosted project lacks all 16 inspected tables introduced by source migrations `0007`, `0008`, and `0009` for Billing V2, field issue, and closeout persistence. It also lacks `d5o_hosted.connected_phase_status` and `connected_phase_projection_v1` from source migration `20261023201553`. Existing hosted business records therefore cannot be assumed compatible with the RC0 application. The source duplicate `0016_p1_01b_2_bid_submission_outcome-ShawnT13.sql` remains excluded exactly as in RC0; no applied migration was edited or repaired.

## Controlled execution plan, currently stopped

1. **Starting state:** require an approved isolated staging copy with its own database, Auth and Storage identities, a complete migration ledger including `statements[]`, and a protected checkpoint. Preserve the 177-entry hosted observation as a comparison, not as authorization to use that project for staging.
2. Compare all 148 shared versions and the 19 name-linked remappings by SQL content, effective schema and object ownership. Classify the 10 legacy entries and 44 otherwise missing released-source files. Determine which absent files are genuinely required, already represented under a different version, or incompatible. Never fabricate applied ledger entries to make `db push` appear clean.
3. Only after the starting schema is proven, construct a reviewed forward bridge for any genuinely missing released prerequisites. Apply corrections as new forward migrations; do not change historical applied SQL. Verify grants, RLS, `SECURITY DEFINER` ownership/search paths, Auth and Storage dependencies, and representative historical reads at each boundary.
4. Apply RC0 manifest orders **212–234**, in the exact filename/checksum order in [the RC0 migration document](D5O_RC0_MIGRATION_MANIFEST.md), only if the bridge and compatibility checks pass. Verify at minimum after organization/onboarding (214–218), lifecycle/configuration (219–223), phase projection (225), service identity (226–228), workforce/Develop (229–233), and final service boundary (234).
5. Verify all 234 intended source effects, actual staged ledger, Work/configuration pins, event and receipt counts, private evidence links, tenant-denial and role-grant probes. Release the application only after its build SHA and database target are bound and tested together.

**Stop conditions:** unknown target identity, ledger divergence without content proof, duplicate version collision, missing backup or private-object checkpoint, unexpected schema/data change, failed RLS/grant check, failed historical pin/replay check, or any protected-command bypass. `supabase db push` against the currently observed hosted project is not an approved execution plan. SQL down migrations do not exist; recovery requires a verified database-and-object restore plus write reconciliation.

The RC1 [disposable upgrade](D5O_RC1_DISPOSABLE_UPGRADE.json) independently reran the clean 211-to-234 chain, applied all 23 forward versions, preserved a fictional tenant, published configuration, pinned Work, event and receipt, and cleaned up. It does **not** establish compatibility with the divergent hosted ledger.
