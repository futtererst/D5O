# RC7 recovery verification

**Local checkpoint recovery: PARTIAL PASS. Coordinated production recovery: UNPROVEN.** A second fresh no-network PostgreSQL container was restored from encrypted schema, database and sanitized Auth artifacts. Measured end-to-end local duration, including container start, was **48.4 seconds**. Recovered counts matched 177 migration rows, 25 Auth users, 25 identities, 15 Work records and 23 Storage metadata objects. All 23 encrypted private objects (2,252,301 bytes) decrypted and matched captured content hashes; their IDs, buckets and paths matched the recovered metadata. See [machine result](evidence/D5O_RC7_LOCAL_RECOVERY_REHEARSAL.json).

The deliberately failed order-215 upgrade ran transactionally and rolled back. Its failed transaction left the original local ledger and key counts intact. This demonstrates rollback of that failure, not recovery after a committed partial upgrade.

The private bytes were verified as encrypted files and against restored metadata, but not loaded into a running local Supabase Storage API. End-to-end serving, Auth sign-in, Storage metadata ID changes and association repair were not demonstrated. The database, Auth and Storage copies were not captured at one logical point. A later production recovery rehearsal requires a coordinated write boundary, verified database and ledger checkpoint, Auth relationships, private Storage metadata and bytes, integrity hashes, actual serving checks, permissions/RLS checks and a measured data-loss window. Restoring an earlier database point after later business events or evidence uploads can orphan files or records and lose approvals/receipts; align both sides of the checkpoint before any cutover.
