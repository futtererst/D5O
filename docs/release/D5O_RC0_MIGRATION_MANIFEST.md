**Ordering and collision.** All 23 new version identifiers are unique and later than the released chain. The main tree contains both `0016_p1_01b_2_bid_submission_outcome.sql` and `0016_p1_01b_2_bid_submission_outcome-ShawnT13.sql`; these share version `0016`. The existing disposable runtime explicitly filters the `-ShawnT13.sql` copy. RC0 retains both historical files unchanged and excludes the duplicate from the executable manifest. A hosted promotion operator must confirm its actual migration ledger before applying anything; a repository filename is not proof of hosted application.

**Forward SQL and grants.** These migrations extend or replace existing command functions in chronological order, including configuration admin, connected service approval/job, tenant capability, Define/Develop guards, Operate review, crew eligibility and current worker schedule reads. They rely on the released hosted schema and `auth`/`storage` roles. The final definitions and their `SECURITY DEFINER`, RLS, and `EXECUTE` grants must be checked against a copied ledger and data in staging before hosted promotion. No historical migration was edited and no hosted migration was applied.

The 23 forward files contain 57 `SECURITY DEFINER` declarations, 18 RLS enablements, 45 `GRANT EXECUTE` statements and 77 `REVOKE ALL` statements by static token scan. Nine function names are defined more than once across these files; the intended final definitions are the last timestamped ones. Notable overrides are `d5o_hosted_configuration_admin_command_v1` (Phase 1, 2C, 2D), service approval (Phase 1/1B), connected pricing/job/create-related-Work and Operate commands (Phase 1B/2F then 2H-TD), crew eligibility (2H-S then 2H-T), and platform provisioning directory (2B then 2C). The fresh and upgrade application runs prove this order compiles. The two-tenant API/RPC suites prove representative grants and tenant denials, while exhaustive hosted privilege comparison remains a staging gate.

**Qualification boundary.** A fresh disposable Supabase stack applied all included migrations and cleaned up successfully. A second disposable stack started with the 211 released-main migrations and seeded a fictional tenant, published configuration version, pinned Work, event, and command receipt. It then applied exactly 23 new migrations with `supabase db push --local`. The tenant, Work identity and pin, event and receipt counts, and all 23 migration-ledger versions remained intact; teardown was clean. See [upgrade machine result](D5O_RC0_UPGRADE_SMOKE.json). This proves a synthetic forward upgrade over representative historical records. It does not compare the hosted ledger or prove every historical evidence object and production fixture. Hosted compatibility and recovery remain staging gates. Recovery requires a tested database backup/restore and application rollback pair; SQL down migrations are not supplied.
