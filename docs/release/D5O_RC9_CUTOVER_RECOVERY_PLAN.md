# RC9 proposed cutover and recovery procedure

**Proposal only; no production write freeze, migration or deployment was performed.** Before a future authorized cutover, identify the exact production project, approved source hashes, 177-entry or then-current ledger fingerprint, object and data inventory, runner privileges, and a compatible release build. Stop if any differ from the reviewed baseline.

1. Restrict all application writes, including business commands, Auth-triggered writes, background jobs and private uploads. Drain in-flight requests and verify no new commands, receipts, events or objects appear during a bounded quiescence interval.
2. Record a consistent database checkpoint containing ledger, Auth relationships, tenant/Work state, permissions, evidence metadata, approvals, receipts and audit. Under the same write boundary, inventory and protect private object bytes and hashes; verify every metadata association resolves. Retain database and object checkpoints together with access restrictions and an operator manifest.
3. Verify restore capability in isolation before making production changes. Verify the exact starting ledger and effective schema, then execute only the reviewed 25 pending source orders with atomic ledger inserts. At 215 run pre/frozen/post in one transaction; stop at first error and preserve logs. Never replay absent early versions or fabricate rows.
4. Compare final catalog, owners, grants, RLS and SECURITY DEFINER functions to the accepted target; verify all protected counts/hashes and business invariants, especially configuration pins, phase events, approvals, receipts, financial state, permits and evidence associations. Deploy compatible application only under separate authorization, perform bounded smoke tests, then re-enable writes after release acceptance.
5. On failure, keep writes disabled, restore the matched database+Auth+Storage metadata and private bytes from the protected checkpoint, verify ledger, object hashes/associations and permissions, then perform operator-approved recovery checks before reopening.

Any write or upload after the checkpoint and before restoration is outside that checkpoint. Restoring only the database can orphan newer bytes; restoring only bytes can orphan metadata or business events. A future coordinated checkpoint rehearsal must measure quiescence, capture skew, restore duration and the actual recoverable data-loss window. This RC9 local rehearsal does not establish production RTO/RPO or atomic recovery.
