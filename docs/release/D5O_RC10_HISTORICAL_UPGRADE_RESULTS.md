# RC10 historical upgrade results

Three fresh, network-disabled local historical restores were inspected. The first revealed local grant overexposure; the second verified ACL reconciliation but used `supabase_admin` as the migration runner and produced local owner drift. The final restore received the production-matched ACL reconciliation, then executed the reviewed 25 migrations as local `postgres`. This final rehearsal, not the earlier two, is the candidate evidence. All restores were from the previously authorized encrypted checkpoint outside Git.

Final ordered run: **177 → 202 actual ledger entries; all 25 source orders 212–236 applied**. Order 215 recorded three bridge/source SQL statements in one transaction. The 259 pre-existing table counts had no unexpected changes; ten targeted historical hashes (Auth users/identities, memberships, invitations, Work, events, configuration versions, customer evidence, public audit and Storage metadata) matched. The database ended with 278 tables as 19 new tables were added by the late migrations. All 814 checked foreign keys had zero orphan rows. The latest permit migration uses array ordinality; an isolated synthetic two-permit array with tied timestamps selected the newest appended permit. This verifies the selector expression, not the complete authenticated field-fact command. No historical permit array was changed.

The local pre-upgrade restore verified 177 ledger rows, 25 sanitized Auth users, 25 Auth identities, 15 Work records and 23 Storage metadata entries; 23 encrypted private object hashes (2,252,301 bytes) matched metadata associations. The observed restore times in these local attempts were approximately 34–35 seconds; they are not production RTO. Database and object captures are not one atomic checkpoint. Full Storage API serving was not run.
