# RC12 private Storage API results

**FAIL for the required direct authenticated-user download.** The 23 authorized encrypted objects were restored into a dedicated disposable local volume; encrypted and plaintext SHA-256 hashes, metadata IDs, bucket/path/version associations and 2,252,301 bytes matched. Supabase Storage API v1.84.19 served all 23 objects to its internal service role over HTTP with matching hashes. But a genuine GoTrue user's direct GET returned `400 not_found`; a second-tenant user, anonymous client, and missing-object request also returned 400. The restored `storage.objects` table has RLS enabled and **zero SELECT policies**, so no direct user positive control exists. These identical errors do not prove tenant- or revocation-specific Storage policy decisions. No policy or grant was weakened. [Byte restore](evidence/D5O_RC12_PRIVATE_BYTES.json) and [direct API results](evidence/D5O_RC12_STORAGE_API_PROBE.json) record the boundary.

The frozen application's server-mediated evidence route **does** work with a genuine GoTrue session: index 200 (16 visible entries), download 200 with receipt hash match, wrong Work 403, anonymous 401, removed membership with existing session 403. The server uses its own membership/Work check before an internal privileged Storage fetch. A scan of 210 client static files found no local service-role token. This is distinct from direct Storage authorization. [Application evidence](evidence/D5O_RC12_APP_EVIDENCE.json) supports these results.

Release decision required: either justify a narrowly scoped direct `storage.objects` SELECT policy against tenant/Work/evidence associations and test it in isolation, or explicitly establish the server-mediated route as the approved access contract. RC12 did neither, so the user-requested direct gate fails.
