# RC8 security and recovery

The role check is validated, the pilot guard trigger is enabled, and its new receipt table has RLS. `anon`, `authenticated` and `service_role` have no SELECT grant on the receipt; `anon` has no execute grant on the guard. A rollback-only synthetic actor could call the Work read RPC for its own workspace, received SQLSTATE `42501` for another tenant, and again received `42501` after its membership was suspended. A rollback-only provisioned-tenant test rejected a field-worker invitation with `42501`, while a pilot proposal update passed. [Guard tests](evidence/D5O_RC8_INVITATION_GUARD_TESTS.json), [tenant tests](evidence/D5O_RC8_TENANT_ISOLATION.json) and [foreign-key results](evidence/D5O_RC8_LOCAL_FK_VALIDATION.json) retain sanitized results.

The historical table counts and targeted hashes cover Work pins, events, evidence, audit and the invitation, but active command-receipt uniqueness, financial behavior, no reopening of completed Work, and the full privileged-function/RLS grant diff were not behaviorally retested. These remain release checks before production promotion.

The RC7 pre-upgrade local restore took **48.4 seconds**. RC8 encrypted a post-upgrade schema/data checkpoint outside Git and restored it into a second fresh network-disabled container in **34.52 seconds**. The recovered state had 202 ledger entries, 25 sanitized Auth users, 25 identities, 15 Work records, the bridge receipt and its RLS/validated check. All 23 private files (2,252,301 bytes) matched captured hashes and recovered Storage metadata associations. See [post-upgrade recovery](evidence/D5O_RC8_POST_UPGRADE_RECOVERY.json).

Local Storage API images exist, but private bytes were verified as encrypted files and metadata associations, not served through a running Storage API. Real-user authentication was not tested. The database/Auth and Storage captures were not one atomic checkpoint; a bounded application write freeze and coordinated database, ledger, Auth, metadata and object-byte protection are required for production cutover. Restoring only a database checkpoint after later evidence uploads or business events can create missing associations or lose later approvals/receipts. Actual coordinated production recovery and its data-loss window remain unproven.
