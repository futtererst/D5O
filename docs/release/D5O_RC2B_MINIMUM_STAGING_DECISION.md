## Fail-closed application contract

The RC2-B code adds a `staging` command runtime without changing the existing production project allowlist or local target list. Staging requires an exact non-production Supabase project ref and URL, `NODE_ENV=production`, database/Supabase operating modes, a Vercel **Preview** deployment with matching system project ID and Git branch, and SHA-256 fingerprints of the staging publishable and server keys. It rejects legacy key aliases on staging to remove ambiguous precedence. The fingerprints must be recorded independently from the approved staging project's credentials; they detect swapped variables but do **not**, by themselves, prove which Supabase project issued an opaque key. Before deployment, make read-only authenticated API calls to the staging project with each supplied key and verify provider acceptance without printing the keys. Runtime origin checks accept HTTPS same-origin scheduling on staging. Invitation delivery remains restricted to the exact test-recipient allowlist because `administrator_approved` delivery is reserved for production.

Required branch-specific Preview variables: `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`, `SUPABASE_SECRET_KEY`, `D5O_HOSTED_ENABLED=1`, `D5O_COMMAND_RUNTIME=staging`, `RYBEXOS_RUNTIME_MODE=production`, `RYBEXOS_AUTH_MODE=supabase`, `RYBEXOS_DATA_SOURCE=database`, `D5O_STAGING_SUPABASE_REF`, `D5O_STAGING_PUBLISHABLE_KEY_SHA256`, `D5O_STAGING_SECRET_KEY_SHA256`, `D5O_STAGING_VERCEL_PROJECT_ID`, `D5O_STAGING_GIT_BRANCH`, exact test-recipient configuration, and an accurate source SHA. Vercel system variables `VERCEL`, `VERCEL_ENV`, `VERCEL_TARGET_ENV`, `VERCEL_PROJECT_ID` and `VERCEL_GIT_COMMIT_REF` must be exposed. Do not set legacy `NEXT_PUBLIC_SUPABASE_ANON_KEY` or `SUPABASE_SERVICE_ROLE_KEY` for the staging branch. Verify the effective Preview variable **names and scopes**, target URL and key acceptance before deployment; never copy production key values.
