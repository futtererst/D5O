# RC4 delivery-stage field-change coverage

The existing field-change domain can govern additional delivery scope **after package Design acceptance** without opening a post-handover connected-service child. RC4-A exercised the commercial Scope path for two tenants through authenticated browser controls on application `96f1b7bccec690c1dec26cf66a55e9526f1619f9`; see [machine evidence](evidence/D5O_RC4A_SCOPE_CHANGE_BROWSER.json). The remaining Scope-specific execution-hold cases are listed in the [RC4-A decision](D5O_RC4A_RELEASE_DECISION.md).

| Contract question / action | Classification | Evidence and qualification limit |
| --- | --- | --- |
| Identify a package-specific issue with report/evidence linkage | SUPPORTED AND VERIFIED | `raise` validates package, accepted release, assigned worker and report/evidence scope; RC3-C records one browser-raised Correction per tenant. |
| Independent assessment and unresolved-change execution hold | SUPPORTED AND VERIFIED | `assess` excludes the creator; trigger `guard_field_change_deploy_v1` blocks protected completion. RC3-C records the rejection and independent resolution before completion. |
| Classify additional scope and record scope, cost, price and schedule impact | SUPPORTED AND VERIFIED | Both tenants' Operations users assessed Scope change; project managers saved a USD 15,000 priced proposal with cost and schedule basis through the browser. |
| Independent internal approval and customer authorization | SUPPORTED AND VERIFIED | Independent administrators approved both proposals. Browser uploads retained purpose- and revision-bound private customer PDFs; forged and missing evidence were denied with unchanged state. |
| Revised Design basis, independent review and package reauthorization | SUPPORTED AND VERIFIED for revised release | Both tenants recorded field-origin Design changes, independently acknowledged holds and reviewed/accepted newer releases. Scope resolution then succeeded from My Work. Actual field-start reauthorization remains unexecuted. |
| Audit, command replay and tenant boundary | SUPPORTED AND VERIFIED for tested cases | Both tenants had 7 change events and 7 receipts after resolution; exact replay returned HTTP 200, concurrent conflicting reuse returned 409. Cross-tenant, wrong-role and stale review attempts were denied with unchanged state. Removed/suspended authority and first-writer concurrency remain unexecuted. |
| Unresolved Scope change blocks protected execution | SUPPORTED BUT NOT FULLY QUALIFIED | SQL guard blocks new authorized permit, completion, turnover and Work acceptance; RC3-C exercised a Correction hold. RC4-A rejected premature Scope resolution but did not reach valid scheduled field-start/acceptance prerequisites while Scope remained open. |
| Delivery change before an accepted Design release | INCORRECT ACCEPTANCE ASSUMPTION | `accepted_release_required` applies before `raise`. Earlier Design/Develop preparation is outside this field-change contract. |
| Post-handover service as a delivery change | INCORRECT ACCEPTANCE ASSUMPTION | Service intake requires Support Active and creates a separate child Work; see [RC3-C contract](D5O_RC3C_CONNECTED_SERVICE_CONTRACT.md). |

**Product gap determination:** no material missing capability is demonstrated for the browser-qualified commercial path after Design acceptance. The remaining execution-hold and reauthorization proof is a **qualification gap**. The connected-service USD thresholds do not apply to this field-change command; both tenants require independent internal review regardless of their service threshold. A requirement for a separate Scope threshold, for changes before accepted Design, or for a distinct executable child job during parent Develop needs a scoped product decision. Do not treat implemented source checks as executed browser proof.
