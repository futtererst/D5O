# RC11 historical integrity and recovery

**Historical restore PASS within local scope; full historical preservation and coordinated production recovery PARTIAL.** The pre-upgrade checkpoint restored with network mode `none`, 177 ledger rows, 25 Auth users, 25 identities, 15 historical Work records, and 23 Storage metadata rows. The upgrade reached 202 actual ledger rows. The RC10 invariant and ACL evidence remains the previous baseline; RC11 rechecked the D5O ACL, protected object hashes and associations, but did not produce a new complete before/after digest for every historical business-history class. Synthetic Work and Storage probes were isolated to the disposable upgraded database; no historical customer Work or permit array was modified.

After HTTP and Storage testing, a new isolated recovery restored the same checkpoint in **26.45 seconds** ([measurement](evidence/D5O_RC11_POST_TEST_RECOVERY.json)). The first attempt hit a transient PostgreSQL startup race after `pg_isready`; that disposable container was discarded. On the successful restore, an injected SQLSTATE `P0001` after DDL inside a transaction left no probe table and retained ledger 177, Auth users 25, Work 15, and Storage metadata 23 ([gate matrix](evidence/D5O_RC11_RECOVERY_AND_GATE_MATRIX.json)). The earlier RC9 bridge-specific four-phase rollback proof remains applicable; RC11 did not rerun those four probes.

The database and Storage captures were not atomic. The 26.45-second local measurement is not a production RTO. A future cutover needs an authorized write restriction, drained commands/uploads, a quiescence check, one consistent database/object inventory boundary, protected backups with hashes, reviewed migration execution, schema and historical-record checks, compatible deployment under separate authorization, smoke tests, then write resumption. Transactions or uploads after the checkpoint would be lost or orphaned on restoration unless separately reconciled. No production freeze was imposed.
