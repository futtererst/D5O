# RC8 migration 215 invitation root cause

**Explained.** Frozen source order 215, `20261023140000_d5o_phase2b_tenant_onboarding.sql`, replaces `d5o_hosted.admin_identity_requests_role_check`. Its new `requested_role` list permits eight organization roles, or `admin` when `provisioning_workspace_id=workspace_id`; it omits `field_worker`. `action='recovery'` requires a null requested role. The preceding hosted check and source `20261021114905_d5o_field_worker_invitation_proposal.sql` explicitly permitted `field_worker` as an invitation **proposal**, while governed worker binding remained the membership authority. Source order 214's organization invitation acceptance path likewise excludes field-worker role assignment by invitation.

The protected historical copy has exactly one `action='invite'`, `requested_role='field_worker'`, `status='setup_completed'` row. It predates order 215, has completion time and provider-user association, resolves to an Auth user, and that user has an active `field_worker` membership in the same workspace. There is no inbound foreign key to the invitation table, and bounded joins to selected command/event tables found no direct same-command reference; the row itself remains business and audit history. Rewriting its role or completion status would misstate the original invitation and could obscure how the valid worker membership arose.

The defect is **missing pilot compatibility in the new constraint**, with an overly broad table-level restriction applied while Phase 2B says existing pilot workspaces are not enrolled in the new tenant lifecycle. The historical row was valid under the prior constraint and is not evidence of an invalid user. The raw row, user identity and email are retained only in encrypted local artifacts and isolated databases, never in Git.
