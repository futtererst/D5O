## Recovery objectives for owner decision

**Proposal only:** recovery time objective of **8 hours** from declared incident to a limited, validated cohort; recovery point objective of **24 hours maximum** for database decisions **and private bytes**, conditional on a verified daily managed checkpoint plus a separately completed object backup and a reconcilable post-checkpoint ledger. The 3m55 empty managed restore and ~15m24 local logical drill do not demonstrate these targets at production scale. If the selected checkpoint/object backup cannot meet them, keep writes paused and obtain a new owner decision. No PITR purchase is assumed.

## Before writes resume after any restore

1. **Declare and freeze.** Release owner pauses application, worker, import, scheduled and direct administrative writes; records UTC start, active deployment ID, schema/migration versions, and the last durable Work, event and command-receipt IDs/revisions. Block old generic-writer traffic before applying the first outstanding protected-write migration. Record any in-flight command IDs for reconciliation.
2. **Choose a matched checkpoint.** Database operator selects a named managed physical backup and records its UTC time, retention window and restore target. Storage operator exports **original private bytes separately** for every required bucket/object through a supported Storage download or S3-compatible path, recording bucket, exact object path, object ID, version/update time, byte length, MIME type, SHA-256, and backup URI. Export the `d5o_hosted.customer_decision_evidence` receipt inventory too: workspace/Work ID, purpose, scope ID and revision, exact basis, evidence ID, `storage_object_id`, `object_path`, `storage_updated_at`, checksum and size. Include other retained evidence/turnover objects and their linking rows. The object manifest must correspond to the database checkpoint; retain any newer objects in a separate post-checkpoint delta.
3. **Protect the backup.** Security operator writes the encrypted, access-controlled byte archive and signed/hash-checked manifest to the owner-approved off-project location. Grant only named recovery operators, record custody and restore-tested decrypt access, and prohibit overwrite/deletion until the approved retention window ends. Database backups contain Storage metadata, **not** file payloads ([Supabase backups](https://supabase.com/docs/guides/platform/backups); [Storage downloads](https://supabase.com/docs/guides/storage/management/download-objects)). The local drill's Linux filesystem extended attributes are **not** a hosted Storage export/import method.
4. **Restore database to an isolated target first.** With explicit incident/release authorization and verified cost, use Supabase Database → Backups → Restore to a New Project for the named checkpoint. Record start/end, new reference and inherited configuration. Keep it inaccessible to customers and outbound jobs. Restore-to-new-project copies database/Auth rows and encryption root key but requires independent Storage objects/settings, Auth settings/API keys, Realtime, Edge Functions and extension/settings review ([Supabase restore documentation](https://supabase.com/docs/guides/platform/clone-project)). Verify Auth users, memberships, worker bindings, Work/parent links, events, command receipts, migration history, RLS, grants, extensions and buckets against the checkpoint manifest. Do not rewrite the 12 applied migration versions. If the target needs candidate migrations, apply only the [48-file mapping-aware manifest](./d5o-production-migration-manifest.md) in order, stopping on first failure.
5. **Restore private bytes without breaking receipt identity.** Recreate bucket settings/policies under the approved configuration, then use a **provider-supported Storage recovery method** for the original bytes and exact paths. Before admitting a customer-decision receipt, confirm the restored `storage.objects` row still has the receipt's object ID, update timestamp, MIME and size, and that an authorized application download returns the saved SHA-256. A normal re-upload may change object ID/update time and is **not** an acceptable silent repair. If the supported method cannot preserve the receipt binding, stop: do not edit immutable receipt/history rows or claim recovery. Escalate to the Storage operator/Supabase support for a supported metadata-preserving recovery or an explicitly reviewed forward-repair design. This hosted step has **not** been demonstrated by the local xattr drill.
6. **Reconcile after the checkpoint.** Compare source/cutover high-water marks with restored Work revisions, events, receipts, package sets, accepted turnover scope and object manifest. Build an itemized delta of post-checkpoint decisions, uploads, publications and worker responses. For each missing item record original command ID, actor/role, source revision, dependent evidence bytes and status. Replay only commands whose exact prerequisites, membership/independence and idempotency still pass; conflicting, stale or unverifiable decisions go to accountable review. Never copy terminal statuses, fabricate approval or overwrite a retained PDF. An unresolved delta keeps writes paused.
7. **Qualification and switch gate.** Independently signed-in operators check exact build SHA, authorized PDF retrieval and SHA-256, wrong-role denial, one compatible typed command with exact replay and stale rejection, protected generic-write denial, current acceptance/package scope and one Finance narrow action on controlled data. Verify historical prototype decisions stay historical and the partially covered request stays Partially covered with its child started but incomplete. Release owner records the comparison and authorizes any limited-cohort routing separately. Restore failure, mismatched bytes/object identity, lost Auth or policy state, irreconcilable receipts, or incompatible app/schema triggers continued write pause and owner escalation.
