# Phase 2H-R root cause analysis

Baseline `f53aa89192b776221067cc6a761248e87259f82e`. Conclusions below are based on source and the prior disposable browser results, not on architecture intent.

| Hypothesis | Finding and code evidence | Employee impact | Correction |
| --- | --- | --- | --- |
| RC1 fragmented action integration | Confirmed. `CustomerWorkExperience.command`, `saveDefineDraft`, and `respondDesignReceipt` each construct their own request, error, and reload cycle. `prototype-design-command/route.ts` separately routes Design RPCs but rejects every nonpilot workspace. | Adding each customer Design decision repeats adapter/UI work. | Use one bounded customer action request and a shared client executor; keep specialized business forms. |
| RC2 incomplete My Work routing | Confirmed. `customer-work/route.ts` labels every `d5o_hosted_role_actions_v1` row `view_only` although that RPC emits Design review responsibilities. `customer-work-tasks.ts` only derives Define and Design receipt tasks. | Employees see Design reviews as context links, without decisions. | Derive actionable Design tasks from hosted Work state, retain role queue for other context, and reconcile tasks after each command. |
| RC3 missing prerequisite visibility | Confirmed. `d5o_hosted_design_release_command_v1` validates issued document, required reviews, dated crew demand, method and package basis; `CustomerWorkExperience` showed only package and accepted-release counts. | An owner cannot see or resolve release blockers. | Show the exact supported Design preparation steps and server outcomes on the Work action surface. |
| RC4 task/business-state divergence | Partly confirmed. Existing Define/receipt tasks derive from Work state and disappear after successful decisions, but generic role rows remain `view_only`, and missing Design tasks cannot hand off to the next actor. No separate completion table was found in this path. | A completed backend decision can coexist with a nonactionable employee queue. | Derive Design task availability from the latest authoritative Work projection; reload list and detail after command success or conflict. |
| RC5 inconsistent evidence handling | Confirmed. `design-document-evidence/route.ts` provides private PDF upload, hash verification, scoped read and hosted evidence registration; the tenant-neutral customer Work page never rendered `DesignDocumentEvidence`. Its isolated-customer read gate required an `Origin` header on same-origin GET, which browsers omit. | An uploaded PDF could not be recovered after reload; the submit control remained disabled. | Reuse the existing evidence component and accept a same-origin GET only on the exact isolated loopback host, while retaining authenticated tenant/document authority. Production general-customer routing remains a release dependency. |
| RC6 misleading qualification | Confirmed. `run-phase2f-connected-journey.mjs` executes later Design decisions by direct RPC while its aggregate reports 48 passing checks. `D5O_PHASE2H_COMPLETION_ACTION_MATRIX.md` explicitly distinguishes that from browser execution. | Aggregate passes overstate employee action coverage. | Emit per-action origin, actor, task/phase before and after, HTTP/RPC result and evidence; calculate browser coverage from the inventory. |

The hosted Design commands already implement the business rules, idempotency receipts, tenant checks and independent reviewer authority. This package does not create a new workflow or evidence engine.
