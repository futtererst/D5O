# Phase 2H-TE Gate B root cause

Baseline: `7f5a5cd0dd9626f582e64c768b1aff1c3e185f53`. Scope: the inherited Phase 2H-TB Gate B assertion `authenticated tenant-neutral Work UI and API isolation`.

The instrumented browser submitted `POST /api/d5o-hosted/connected-work?workspace=tenant_a_test` as the authenticated tenant administrator. The command returned HTTP 201 and persisted one tenant-owned Work and one command receipt. The page nevertheless had no visible `Connected Work created` status. The event timeline showed a second navigation to the same route, with no page error. The create component held its success message only in React state, which was lost on that remount. This explains why the newer TC/TD journeys could pass while the inherited Gate B presentation assertion intermittently failed. The red run retained 50/51 assertions and verified disposable cleanup in [the original failing result](evidence/phase2hte-gate-b-red-results.json).

The customer Work component now saves the **confirmed** Work reference in workspace-scoped session storage only after HTTP 201 includes a presentation ID. On remount it asks the authenticated customer Work API for that exact Work ID and title before restoring the visible confirmation. A new create attempt clears the old hint. This adds no business authority to browser storage: the server response and subsequent authorized read govern the message. The focused reload probe requires visible confirmation after reload, exactly one persisted Work, and exactly one command receipt.

Instrumentation exposed a separate inherited test-loop defect. The runner waited for a receipt after a successful POST but did not leave its two-attempt loop. When the receipt appeared after the immediate visibility check, the runner submitted the same form a second time using a different command ID. The [duplicate red result](evidence/phase2hte-gate-b-duplicate-red-results.json), [request/response timeline](evidence/phase2hte-gate-b-duplicate-red-diagnostic-a.json), and [database probe](evidence/phase2hte-gate-b-duplicate-red-reload-a.json) show two HTTP 201 creates, two distinct Works, and two receipts. The runner now exits immediately after the awaited receipt. This retains the visible-success assertion and strengthens it with persisted-state and replay safety checks.

The reload probe originally checked visibility immediately after navigation, before the authorized revalidation fetch completed. It now waits for the rendered confirmation itself, with a bounded timeout and no arbitrary sleep. That first attempt is preserved in [the result](evidence/phase2hte-gate-b-first-green-attempt.json) and [probe](evidence/phase2hte-first-reload-probe-a.json).

The diagnostic records synthetic form values, browser route, request method and destination, HTTP status/body, authenticated fixture actor and workspace, DOM status/alert state, navigation events, persisted Work and receipt references, and actual browser screenshots. It does not record Auth tokens. The create API and hosted command were not changed.
