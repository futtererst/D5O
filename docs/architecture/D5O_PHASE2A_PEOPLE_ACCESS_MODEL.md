# Phase 2A people and access model

`auth.users` owns login identity. `d5o_hosted.memberships` owns one role and access status per workspace/user; a user can have multiple independent workspace memberships. `connected_crew_profiles` owns tenant workforce identity, qualifications and capacity, including people without login. The optional profile `actor_user_id` binds a workforce person to a login without making the two objects identical. Organizational assignments reference these existing rows; they do not mint a second employee ID.

The existing `admin_identity_requests` ledger records invitation email, workspace, proposed role, inviter, reason and provider outcome. Phase 2A adds expiry, acceptance and revocation facts. `d5o_hosted_org_invitation_request_v1` rejects admin and field-worker role proposals, serializes by tenant/email and rejects duplicate live offers. The server uses the existing Supabase Auth Admin invite only for an approved pilot recipient; provider acceptance is recorded separately from verified delivery. An already confirmed Auth user receives an offer without a new email. The recipient's authenticated `accept` command checks email equality, confirmation, provider user ID, tenant, exact offer, expiry, revocation and approved role before creating or restoring a tenant membership in one transaction. Replay is safe. A tenant admin may revoke an unused offer. Expired and revoked offers cannot grant access.

Tenant administrators can change approved existing roles, suspend, reactivate and remove non-protected memberships with an expected revision and audit reason. Self-role changes and modifications of protected admin or field-worker memberships are denied. Removal marks the tenant membership `removed`; it does not delete the global Auth user or historical workforce profile. All protected hosted commands continue to require status `active`, so a live token loses tenant authority immediately after suspension or removal. Administrator succession and worker binding retain their existing governed paths.

Live email delivery and commercial recipient onboarding remain unqualified. The production pilot recipient allowlist stays in place. Synthetic tests use confirmed local Auth users and do not send real mail.
