# D5O work-surface visual audit

Date: 2026-10-15. Tested application: `a14d1fac0403b9447145be77f9af2a82d4eb41a8`, isolated production-mode preview on port 61652. This is a presentation assessment, not a business-command or usability qualification. Shawn's feedback is that the app feels visually inconsistent and harder to engage with than mature SaaS products; the observations below are from fictional pilot accounts and rendered pages, not invented user-session results.

## Verdict

D5O has a recognizable navy/gold identity and working role-aware navigation, but it does not yet have one coherent application design system. The new My Work split view points in a useful direction. Most other surfaces still combine oversized repeated headers, several competing card styles, tiny uppercase metadata, long prose, raw technical identifiers, and different interaction patterns for similar tasks. Fixing one screenshot at a time will keep recreating the inconsistency.

The largest visual defects observed in the current build are:

1. The Work Record overview has overlapping text in its phase-decision panel at 1440px, making a key status unreadable.
2. The handoff register renders many lines of receipt, actor and source IDs in one narrow table cell; at 390px its table columns are clipped inside the register.
3. The Develop view repeats the same field-change explanation in adjacent panels before its actual solution/offer work.
4. The execution register gives a large dark sidebar to a recording rule while the package table is compressed; its useful content begins below the first viewport.
5. Phase pages repeat the long Work title, six-phase navigation, another large phase title, metric cards and further tabs before a user reaches the current task. On a phone, the task is below the first viewport.
6. My Work, Crew, People and Work hub use a sans-serif title around 27–31px while Discover, Define, Portfolio and most other pages use a serif title around 43px. Content density and control treatment vary accordingly.
7. Critical facts often use 10–11px uppercase or low-contrast secondary text. The mobile audit found many text leaves below 12px on phase, scheduling, handoff and evidence pages. These are descriptive counts, not an accessibility certification.

## Shared product direction

Keep the navy/gold brand, but make the work application a consistent, task-oriented product:

- **Five page archetypes:** task workbench, searchable register, planning canvas, Work Record detail, and administration. Every routed surface must choose one archetype. A phase is context for a task, not a second full dashboard inside a record.
- **One app frame:** shared sidebar and top bar, one page title, one content width rule, one responsive gutter. The Work Record should use its available width instead of a narrow 800px column beside unused canvas. Collapse its long title to a compact sticky identity line after entry.
- **One typography scale:** use a legible UI sans for application headings, labels, body and data. Reserve expressive serif for brand or editorial moments outside daily work. Suggested roles: page 26–30px, section 18–22px, row title 14–16px, body 14px, supporting text 12–13px; avoid sub-12px task information. Use weight and spacing rather than all caps everywhere.
- **One spacing/control scale:** 4/8/12/16/24/32px spacing; 40–44px controls; standardized 8px card radius, borders and elevation; predictable compact and comfortable density modes. A user should not meet a different form design in each phase.
- **One icon language:** extend the existing `PlatformIcon` set to cover objects and actions (work, customer, site, package, document, crew, asset, review, hold, accepted, money). Use consistent 16/20px stroke, alignment and accessible labels. Icons support text; they do not replace status words.
- **One status vocabulary:** use clear labels and semantic colors for Draft, Needs action, Waiting, Held, Returned, Reviewed, Accepted and Historical. Make current versus superseded unmistakable. Gold means primary action or selected navigation, not a generic warning.
- **One task frame:** title and outcome; customer/site/package identity; current source revision; blocker; essential evidence; permitted controls; saved result and next owner. Put provenance and full history behind a deliberate secondary action. Preserve exact scope, safety and required evidence in view.
- **One responsive strategy:** at phone width, replace multi-column registers with stacked record rows or a selected-detail view. Phase navigation becomes a compact progress/menu control. The primary action and blocker remain reachable without scrolling past an oversized title and six large phase tiles.
- **One writing style:** replace architecture phrases such as “current committed position” and “receiving responsibility” with plain task language in the foreground; keep precise authority terms in the detail view. Show why data is requested and what happens after saving it.

These recommendations align with the use of shared design tokens and spacing in [Atlassian Design](https://atlassian.design/foundations) and clear type/layout hierarchy in [Fluent 2](https://fluent2.microsoft.design/layout). They are references for system discipline, not a proposal to copy another brand.

## Implementation order

1. **P0 visual defects:** fix Work Record text overlap, duplicate Develop callout, execution register layout, handoff register density and mobile clipping. These are observed failures, not merely style preferences.
2. **Shared foundation:** consolidate tokens and primitives now split across `enterprise.css` (1,251 lines), `D5OVisualSystem.module.css` (217 lines) and page-specific modules. Build shared `PageHeader`, `TaskFrame`, `StatusBadge`, `Metric`, `DataRow`, `Field`, `Button`, `EmptyState`, `DetailDrawer` and `ResponsiveRegister` components. Migrate existing surfaces rather than stacking another override layer.
3. **Record shell:** one compact identity header, current decision and blocker; phase controls become secondary navigation. Use full available width for phase workspaces, with a consistent detail rail only when it contains actionable information.
4. **Task and register archetypes:** My Work becomes the common task model; Discover, Define, Develop, Design, Deploy, Operate and Finance adopt its hierarchy. Portfolio, Evidence, Execution and Handoff adopt one register system; Crew keeps a specialized calendar within the same tokens.
5. **Mobile and writing:** replace tables with mobile row/detail layouts; keep task and blocker above the fold. Rewrite foreground labels into plain-language outcomes, with technical terms and IDs in provenance.
6. **Visual QA:** compare every surface at 1440px, 1024px and 390px with the same fictional role fixtures. Check typography, controls, keyboard focus, color meaning, loading/empty/error states and the first actionable viewport. Have Shawn review the resulting design before claiming user acceptance.

Presentation changes must not alter role eligibility, source revisions, typed-command outcomes, evidence custody, audit history or tenant boundaries. This audit did not submit business commands or conduct a Rybex-user session. Several role-restricted pages redirected to My Work for the pilot role; their source was inspected, but their full state was not visually qualified here.
