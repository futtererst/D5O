# D5O enterprise implementation roadmap

Baseline `origin/main` `4cf881b5`; references below are inspected code/migration **[C]**, test source **[T]**, or prior documentation **[D]**. This is a plan; no implementation, migration or deployment was performed.

## Critical path

`P0-A boundary inventory → P0-B disposable two-tenant proof → P1-A hosted policy authority → P1-B tenant admin generalization → P1-C service threshold command → two-tenant acceptance`. Phase-wide policy expansion and platform operations follow the same qualified command and version pattern. Retain pilot allowlists until P0-B and P1-B replacements pass. The smallest proof is independent $10,000/$25,000 policies on the same code with an immutable $15,000 decision trace and cross-tenant denials.

Each package is independently reviewable and revertible. “Rollback” means code/feature rollback plus preserving existing records; published configuration and decision history are never deleted.

### P1 — Configurable operating policies

**P1-E: Server service decision and historical trace (L; risk medium).** Objective: enforce B's and A's service threshold in one authoritative command. Reuse hosted pinned work version and RPC receipt/event pattern in `20261008230000_d5o_connected_work_identity.sql` and `20261019213000_d5o_hosted_configuration_management.sql` [C]. Change service request decision RPC, API, record/event schema and tests. Dependency: P1-B, P1-C. Acceptance: $15,000 requires added approval under $10,000 A policy and follows $25,000 B policy, same build; event stores amount, actor, workspace, version, evaluated rule and result; rollback applies to new work only. Security: B record under A actor, forged amount/version, replay, stale config, segregation of duties. Regression: existing connected service work and invoices. Migration/rollback: additive event/pin fields, dual-reader for old work, feature gate; retain events on rollback.

**P1-F: Phase policy migration slices (XL total, deliver as six S/M slices; risk medium per slice).** Objective: connect approved hosted policy to Discover, Define, Design, Develop, Deploy and Operate commands in that order, one phase per release. Reuse `components/d5o/platform/published-phase-configuration.ts`, `lib/d5o/prototype-work/{define,design,commercial,deploy,operate}-command.ts` [C]. Change phase-specific RPC/validator/API and tests; preserve fixed six-phase lifecycle and financial/evidence invariants. Dependency: P1-A and P1-E pattern. Acceptance per slice: new work reads pinned version, old work keeps historical verdict, unauthorized phase transition denied; six-phase end-to-end journey passes after last slice. Security: cross-tenant and wrong-role phase command, evidence bypass. Regression: existing pilot journey and historical record rendering. Migration/rollback: additive versioned fields, old reader maintained, feature gate per phase, no historical recomputation.
