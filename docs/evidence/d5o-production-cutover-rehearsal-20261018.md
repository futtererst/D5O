Each transaction also recorded its successful version/name in that isolated migration ledger. No file was edited to make the rehearsal pass. After the normal-role run, the source counts above were unchanged, canonical Work remained at zero, no database constraint was left unvalidated, and all 140 regular `d5o_hosted` tables had RLS enabled. The hosted source still had its original 22 migrations, 7 Auth users, 3 D5O memberships and zero Storage objects when rechecked.

**Conclusion:** the selected application-data export was actually restored, and this restored live-schema/data snapshot accepted the complete pending SQL sequence under both local database roles. That resolves the previously unobserved populated **SQL cutover compatibility** question for this snapshot. It does not establish a complete disaster-recovery backup of every Supabase-managed service, an off-host durable backup, live Auth/API behavior against the upgraded copy, or a tested production rollback after external writes. The temporary files can expire; take and verify a fresh, access-controlled durable backup immediately before any hosted cutover. Production release still requires the open role-separated browser decisions and an exact-build hosted smoke/recovery plan. Do not merge or deploy based solely on this database rehearsal.

After the checks, only the `d5o-release-restore-20261018` local stack was stopped without `--no-backup`: zero rehearsal containers remain running and its two named database/Storage volumes remain.
