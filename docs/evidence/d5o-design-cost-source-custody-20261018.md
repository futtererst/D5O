Supabase database backups contain Storage metadata but not deleted object bytes. (C) If only D5O records and backup bytes survive, the supported Storage API can create an object but does not promise the prior `storage.objects.id`/`updated_at`. The installed exact-generation guard would reject a different object; no identity-preserving hosted restore or governed replacement relationship is installed or locally qualified. This is a **bounded unimplemented recovery mode**, not evidence that cases A/B fail. Do not directly edit managed Storage rows or rewrite the original receipt to make C pass.

**Finding and procedure correction.** The existing contract is recoverable when the provider-supported restore retains both original metadata identity and identical bytes. No application or migration defect was demonstrated for that contract, so no recovery feature was added. The production procedure must first identify whether its method actually preserves the object generation; a database-only backup plus generic re-upload cannot be claimed as qualified. On a frozen, explicitly authorized isolated target, the operator must inventory the original receipt and object metadata, restore Auth/database ownership and migration markers with an object-byte checkpoint from the same cut, then use ordinary owner PM and Finance application retrieval to verify hash/size and exact claim. Denied roles must receive byte-free errors. Stop if identity or bytes disagree. If the supported hosted restore creates a new provider identity, demonstrate that failure on synthetic data in a separate target **before** designing an append-only, operator-audited replacement relation and ordinary administration path. No such replacement was attempted here because the current local case B already passes and no hosted-compatible isolated object target/destination was authorized. Do not present the local xattr procedure as a hosted Storage method.

Supabase's [database backup guide](https://supabase.com/docs/guides/platform/backups) states that object bytes are not in PostgreSQL backups; its [Storage schema guide](https://supabase.com/docs/guides/storage/schema/design) directs object operations through the API. The [restore-to-new-project guide](https://supabase.com/docs/guides/platform/clone-project) explicitly excludes Storage objects/settings. These documents do not establish an identity-preserving hosted object restore. The exact remaining hosted check is a provider-supported, owner-authorized isolated restore with a synthetic document, matched database/object backup, recorded cost and encrypted destination, followed by ordinary role-separated application retrieval. No production/shared write or new hosted resource was made.
