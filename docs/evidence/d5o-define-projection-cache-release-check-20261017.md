## Follow-up: save contract, editor recovery, and runtime gate

Follow-up application commit: `47e2de3a5dd84dd5f0e98ab1ed2c6a756ddc2fbe`, based on documentation HEAD `d0595ddbba98f210c1d0a5dba3c38e56f9861755`. The installed cache migration remains `20261017180000_d5o_draft_save_projection_cache.sql`; no forward migration was added.

The effective hosted API accepts a Work draft with `expectedRevision` and invokes `d5o_hosted_prototype_save_v1`. Its installed SQL takes the workspace Work-state row `FOR UPDATE` and rejects a different revision with `stale_prototype_state` (`23505`), which the route maps to HTTP 409 `stale_state`. The typed Define decision separately binds exact source and decision revisions. This is an **explicit stale-state rejection contract**, not an automatic merge contract. A user must compare the current basis and deliberately re-enter applicable draft changes. Neither approved requirements nor a competing decision may be silently replaced.

Source inspection found a distinct editor-recovery defect: on HTTP 409 the editor kept the unsaved React state but told the user to refresh; refresh fetched the shared snapshot and discarded that state. A transport exception also lacked a general failure notice for a Define edit. The focused correction in `D5OPlatform.tsx` now retains changed Define drafts in tab-scoped session storage keyed by workspace and actor, presents draft and current values for comparison/copy, and requires an explicit current-state read before re-entry. It does not auto-merge or resubmit. A 503 or network failure is described as an **uncertain outcome**. The current-state read checks whether the exact retained Define draft already committed; if so, the UI says not to retry and clears the recovery copy. If browser storage cannot retain the copy, loading the current state is blocked while the user copies the in-memory draft. This is implemented behavior, **not yet browser-observed** on the disposable target.
